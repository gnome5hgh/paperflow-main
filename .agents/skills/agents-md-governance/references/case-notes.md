# 现场笔记：客户端怎么装载、以及一次真实改造的记录

判据与模板都是通用的，但**装载行为**决定了内容该放哪。这份笔记记录实测结论、一个真实案例的数字，以及踩过的坑。

## 客户端怎么装载 AGENTS.md

### ZCode（实测：反编译 `app.asar` 与 `glm/zcode.cjs`）

- **只解析两份**：用户级 `~/.zcode/AGENTS.md` + **从当前目录向上走到项目根（以 `.git` 所在目录为界）遇到的第一个 `AGENTS.md`**。
- **不逐层合并**：向上查找**命中即返回**。所以
  - cwd 在仓库根 → 子目录的那些 manifest **全部不进上下文**；
  - cwd 在某个子目录 → 注入的是子那份，**父那份反而不在**。
- **每份上限 `100 * 1024` 字节**，读取是 `readFile().subarray(0, max)` → **从尾部截断**。
- 除 AGENTS.md 外还会自动注入项目上下文（包清单、`Makefile`、`docker-compose.yml`、`Dockerfile`、git 分支与状态）——所以「项目概览」节有一部分与它重复，不必写太长。
- 内置 `/init` 命令自己给的推荐内容清单（可作为内容完备性的对照）：仓库用途与主要目录 / build、typecheck、lint 与聚焦测试命令 / 对改动有影响的架构边界与分层规则 / 编码惯例与导入路径规则 / 本仓特有的坑 / 改敏感区前必读的文档。

### 其他客户端

`agents.md` 开放格式（Linux Foundation 的 Agentic AI Foundation 托管）只规定「就近的文件优先」，**具体是合并还是取一份、有没有长度限制，各家实现不同**；Claude Code 的 `CLAUDE.md` 还支持 `@path` 导入。所以：

- **别把「框架会合并」当作事实**写进 manifest。按「子文件要靠父文件 Routing 被主动读到」来设计——这个假设在所有客户端下都成立。
- 换客户端前，用下面这个方法**空跑验证一次**，不要猜。

### 三十秒验证你所在客户端的行为

```bash
mkdir -p /tmp/probe/sub && printf '# Probe\n\n唯一标记: PLUMBUS-7742\n' > /tmp/probe/sub/AGENTS.md
```

然后在**仓库根**开一个新会话，问 agent「`/tmp/probe/sub/AGENTS.md` 里的唯一标记是什么」。答不出来 → 子文件不会被自动注入，必须靠 Routing 主动读；答得出来 → 你的客户端会向上查找，但仍要确认它是否也合并了父级（同时放两份带不同标记的文件即可测出）。

## 一个真实案例（paperFlow，2026-10-14）

改造前的状态，以及各步的实际收益：

| 项 | 改造前 | 改造后 |
|---|---|---|
| 根 manifest | 413 行 / 77,099 字节（占 100 KB 上限 **75%**） | 200 行 / 约 15.6 KB（15%） |
| 其中「架构百科」节 | 41,492 字符 = **全文 89%** | 删除，设计叙述回归设计文档 |
| manifest 总数 | 13 份 | **24 份**（补齐了 11 个单元的缺口） |
| 全仓合计 | 约 106 KB | 约 90 KB（但覆盖面翻倍） |

动作顺序（有效，可复用）：**先删快照（量大、风险低）→ 再补缺口（把规则放回离使用点最近的 manifest）→ 最后对漂移（修死引用）**。

同一批改造里就抓到四类真实漂移，正好是「快照必然过期」的证据：

1. **同一份清单写了两遍，其中一遍过期**：ADR 按模块划分的编号清单在文件里出现两次，一处列到 0010，而 0011、0012 已经存在。
2. **文件内部叙事过期**：代码里已改名的模块，注释与 manifest 里还写着旧文件名。
3. **薄指针型文件过期最狠**：一个「只做入口摘要」的文件里，写着已退役的依赖、已搬迁的数据目录，以及重复的角色名——因为它同时复述了别人的内容。
4. **规则声明与现场相矛盾**：新写了「正文恒为最新、不留『更新（日期）』痕迹」的规则，转头就发现某份文档里挂着一条更新注记。

## 坑

- **治理规则放进了 gitignore 的目录**。文档目录、实验脚本目录如果不入库，放在那里的 manifest **不会随仓库分发**——新人 clone 下来什么都没有。通用治理留在入库文件里，只有纯本地约定才放那儿。
- **`AGENTS.md` 与 `AGENT.md` 打架**。有的生态用单数 `AGENT.md` 表示「一个角色/插件的契约」。同树并存时，agent 与人都容易读错，**那种目录不要再放 `AGENTS.md`**（案例中就有一个插件目录，每个子目录一个 `AGENT.md`）。
- **瘦身时删掉了真规则**。删之前先把「它有没有别的去处」逐条走一遍（见 `audit-checklist.md` 第 5 步）。判断「是不是真规则」的判据始终是开头那一句：删掉它，agent 会不会做错事。
- **不加节**。维护过程中很容易冒出「临时」节（本次改造、待办、已知问题）。要么并入既有节，要么进设计文档——骨架一乱，机械校验就失效，跨会话也认不出来。
- **不校验就提交**。链接与骨架校验都是几秒的脚本，改完就跑。治理文件是纯文本，**它自己不会报错**——只有脚本会。
