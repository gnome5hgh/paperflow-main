# AGENTS.md 治理

你是正在为一个仓库搭建或维护指令文件（AGENTS.md）的编码 agent。本 skill 给三样东西——**判据**（什么该写、什么该删）、**骨架**（根一份 + 每个单元一份的固定节序）、**流程**（搭建 / 变更 / 体检），三者都与具体项目无关，`references/` 里有可直接抄的模板与清单。

## 一、判据：写规则，不写快照

每条内容落笔前问一遍：**删掉它，agent 会不会做错事？**

- 会 → **规则**，留下：约束、边界、做法、非显而易见的坑、必须成立的不变式
- 不会，但得去源码翻 → **快照**，删掉：字段表、枚举取值、文件清单、当前数量、当前有哪些角色 / 工具 / 端点
- 「设计**为什么**是这样」 → 归 ADR 或设计文档，manifest 里只留一句约束 + 一个指针

唯一保留的非规则是**导航**：目录地图，以及「要改 X 就读 Y」的指针。它不是快照的替代品，是入口——保留，但压到最小粒度（写到「一层目录 + 一行用途」就够，不要逐文件）。

**为什么这条最重要**：快照必然与代码脱节，而**读到的旧快照比读不到更糟**——agent 会照着过期的字段名、已删的文件去写代码，还自以为有依据。

## 二、装载现实：内容取舍的硬约束

各客户端实现不同，但有两个共同点决定了内容该放哪：

- **通常只注入一份**：从当前目录向上找到的第一份 AGENTS.md 就是全部，**不逐层合并**。所以子 manifest 必须靠父文件的 Routing 被主动读到——在父文件里写清「改哪个模块前先读它那份」。别指望框架替你加载。
- **每份有字节上限**：超出即**从尾部截断**（ZCode 默认 100 KB）。因此**不可丢失的红线要放文件前 1/3**，越靠后越容易在某次膨胀中被切掉。
- 用户级文件（如 `~/.zcode/AGENTS.md`）先注入、仓库文件后注入，后者可以覆盖前者的宽泛默认。

实测方法与各客户端差异见 `references/case-notes.md`。

## 三、骨架：根一份 + 每个单元一份

节名与顺序固定——跨项目复用、跨会话检索、以及「这个文件是否完整」的机械校验，全靠它统一。

**根 manifest（工作区总入口，16 节）**

```text
# AGENTS.md
<intro：这份文件给谁看、以及下面那条判据>
## Scope              覆盖范围、事实优先级、子 manifest 如何被读到
## 模块定位            名称 / 路径 / 角色 / 一句话定位 / 绑定环境
## 目录结构            一级（必要时二级）目录树 + 一行用途
### 当前目录分层含义     哪些是事实源、哪些是产物、哪些不入库
## 技术结构            语言版本、依赖声明位置、依赖服务、外部端点
## 环境与依赖          必须提供的密钥 / 必须配的路径 / 哪些依赖是软依赖
## 仓库职责            这个仓库提供什么
## 核心协作逻辑         系统怎么运转（几条，不是教程）
## 硬红线              不分模块、任何地方都必须成立的不变式
## 关键入口            入口文件 / 参数声明点 / 插件契约 / 文档索引
## 渐进式阅读路径       按任务类型给出「先读什么再读什么」
## 调查规则            先读什么、代码与文档冲突时怎么办
## 常用命令            安装 / 测试 / 单测 / 起服务 / 启动，含环境陷阱
## 统一编码规范         注释与命名、与默认不同的风格、复用优先
## 文档维护规则         设计文档怎么改、历史记在哪、manifest 自己的纪律
## Routing            子 manifest 与扩展资源的链接清单
## References         关键文件链接清单
```

**单元（子）manifest（13 节，顺序固定）**

```text
# <目录名>
## Scope                       覆盖范围 + 不重复父级的哪部分
## Module Positioning          角色：`<取自词表>` + 职责一句话
## Directory Structure         子目录/关键文件一行一项（导航粒度）
## Responsibilities            它负责什么（边界内）
## Core Logic                  机制与不变式：怎么运作、什么必须成立
## Key Entry Points            从哪几个文件/符号入手
## Usage And Change Notes      改动注意：改 X 要连带动 Y、新增字段要同步哪几处
## Dependencies And Collaboration  依赖方向与协作边界
## Investigation Rule          出问题先看哪里（可执行的阅读顺序）
## Core Commands               真实可跑的命令
## Verification                证明改动正确的命令
## Routing                     上级 / 同级 / 相关链接
## References                  关键文件链接
```

`Module Positioning` 的**角色**从固定词表取，别自创同义词（便于跨项目检索）：

```text
repo-root-workspace-manifest   工作区总 manifest（多仓/多包根）
repo-root-manifest             单仓根 manifest
aggregator-manifest-dir        只聚合子包、自身不放代码的目录
package-root-manifest          包根（有代码，但它是这一层的入口）
capability-or-domain-leaf-manifest-dir  能力/领域叶子目录（最常用）
shared-package-manifest-dir    被多处复用的共享包
app-manifest-dir / runnable-app-leaf-manifest-dir  可运行应用
bom-or-contract-leaf-manifest-dir  只有契约或清单、没有运行时代码
config-package-manifest-dir    配置模块
asset-root-manifest-dir        资产根（随仓库分发的模板/知识库等）
plugin-root-manifest           插件目录
```

每节该写什么、怎么写，见 `references/root-manifest-template.md` 与 `references/module-manifest-template.md`。**内容分工不要混**：`Responsibilities` 说它是什么，`Core Logic` 说机制与不变式，`Usage And Change Notes` 说改动注意，`Dependencies And Collaboration` 说边界——每条内容只归一处，重复出现就是漂移的种子。

## 四、情形 A：新项目从零搭建

1. **先扫，别先写**：读 `README`、包清单（`package.json` / `pyproject.toml` / `pom.xml` / `go.mod`）、测试目录、CI 配置、`.env.example`、顶层目录树。目标是弄清「有哪些单元、各自的约定是什么」。
2. **定层级**：哪些单元配得上自己的 manifest？判据是**「这个单元有没有自成体系的约定」**——有，就给它一份；只有一两个内聚模块、没独立约定的目录不给（为放 manifest 而放是噪音）。注意：**目录里同时存在代码文件不是禁止项**（多数生态的叶子 manifest 本来就平铺在模块里）。
3. **建根 manifest**：按第三节的 16 节写。`硬红线` 与 `常用命令` 是价值最高的两节，先写它们；`Scope` 里写清「子 manifest 不会自动注入，改模块前按 Routing 去读」。
4. **建子 manifest**：每份 13 节。命令与验证要**真实存在**——写不出可跑的命令就老实写「无」，不要编。
5. **配套定设计文档的去处**：规则里会反复出现「为什么这么设计，见 XX」。若项目还没有，本次一并定一个（如 `docs/adr/` 一份一模块、或 `docs/decisions/`），否则「为什么」永远无处安放，最后会挤回 manifest 变成叙事散文。
6. **体检一遍**：走 `references/audit-checklist.md`，确认没有把快照写进去、没有父子复述、链接都能解析。

## 五、情形 B：模块增删改名

- **新增目录**：先判断它够不够格有自己的 manifest（同 A-2 的判据）。够格 → 按 13 节写一份，并在**父 manifest 的 Routing 与 Directory Structure 各补一行**。父文件里若原本为它写了一段规则，**搬到子文件去，父里只留指针**（否则立刻开始复述）。
- **删除目录**：删掉它的 manifest + **父文件里指向它的所有链接与清单项**；检查有没有别的 manifest 引用它（`grep -rn "<目录名>" --include=AGENTS.md`）。
- **改名 / 移动**：改目录名、改 manifest 的 `# 标题`、改 `Scope` 里的路径、改所有指向它的相对链接与 Routing 条目。**同一批改完**，不要留旧名兼容。
- **拆分（一个大目录拆成两个）**：各自的 `Scope` 要写清「我覆盖哪一半」，父文件里原来那段规则按归属切开分给两份，`Dependencies And Collaboration` 补上两者之间的关系。
- **合并**：留一份、删一份，把两份的规则按节合并去重（同一件事只留一处），改所有引用。
- **只用一条纪律贯穿**：**一次变更同时改完「内容、清单、链接」三样**。缺一样就会留下漂移——而 manifest 的漂移不会被 git diff 顶出来（详见 `references/case-notes.md` 的教训）。

## 六、情形 C：久跑之后重新维护（体检 + 瘦身）

项目跑了几十上百个提交之后，manifest 一定会长歪。按 `references/audit-checklist.md` 逐项过，主线是四步：

1. **量体积**：每份多少行/字节，与客户端上限比（超 70% 就该处理）。找出最大的那几节——膨胀几乎总是集中在某个「模块百科」节里。
2. **扫快照**：逐节问第一节的判据。典型重灾区：配置字段表、目录逐文件清单、枚举取值、角色/工具清单、当前数量。**这些直接删**——真相源是代码。
3. **查复述**：父子文件之间、manifest 与设计文档之间、manifest 与 README 之间，同一件事写了几遍？留最靠近使用点的那一处，其余改指针。这一刀通常比搬去别处更省事、风险更低。
4. **对漂移**：每个链接、每个被点名的路径/文件名/命令，逐个验证是否还存在。改名、搬迁、退役留下的死引用要就地改正——**改正不是历史，是错**。
5. **验骨架**：用脚本核对每份的节名与顺序（见清单里的脚本），确保没有人在维护中漏节或多出临时节。

瘦身之后**必做回归**：把删掉的每一条规则都过一遍「它有没有别的去处」——该记进 ADR 的、该进别的 manifest 的、该进 skill 的。宁可多搬一处，不要让一条真规则消失（这是瘦身最容易犯的错）。

## 七、常见坑（Gotchas）

- **把现状写成规则**：「当前有 8 个 agent」「支持 4 种格式」——今天真、下周就假。改写成「新增角色要同步 X」「格式渲染必须回填不写回」。
- **父子复述**：父文件写一遍、子文件再写一遍，改代码时只改一处。判据是「这条规则最靠近哪个使用点」，留那一处。
- **`AGENTS.md` 与 `AGENT.md` 撞名**：有的生态用单数 `AGENT.md` 表示「一个角色/插件的契约」。同一棵树里两者并存极易误读——那种目录**不要**再放 `AGENTS.md`。
- **给不存在的目录放 manifest**：目录只有一两个文件、没有独立约定，单设一份就是纯维护成本。
- **治理放在不入库的目录里**：若某个目录被 gitignore（如个人笔记、实验脚本），它的 manifest **不会随仓库分发**——通用治理规则要留在入库的文件里。
- **只写「是什么」不写「要注意什么」**：`Responsibilities` 写得再漂亮，也不如 `Usage And Change Notes` 里一句「改这个字段要同时改三处」有用。
- **命令编造**：`Verification` 里写一条从没跑过的命令，比留空更有害。
- **一次只改一半**：加了新模块却忘了父文件的 Routing，等于没加（那份 manifest 永远不会被读到）。
